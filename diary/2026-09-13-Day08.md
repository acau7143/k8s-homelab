## 오늘 처음 안 사실
| 몰랐던 것 | 알게 된 것 | 왜 그렇게 되는지 |
|---|---|---|
| flannel.1 MTU가 1450인 이유 | VXLAN 캡슐화 오버헤드(50바이트)를 미리 뺀 값 | 1500(물리 MTU) − 50(캡슐화 헤더) = 1450 |
| `via X dev flannel.1 onlink` 라우팅 의미 | 실제 게이트웨이가 아니라 ARP+FDB로 진짜 목적지를 찾는 트리거용 가짜 주소 | flanneld가 미리 ARP/FDB 테이블을 조작해둠 |
| kubelet InternalIP ≠ Flannel public-ip 결정 로직 | kubelet은 명시적 설정(advertise-address)을 따르지만 Flannel은 기본 경로 기준 자동 탐지 | Day2에서 Host-only/Internal에 never-default를 걸어 NAT만 기본 경로를 가지게 된 것이 원인 |
| kubelet 에러 5종(런타임다운/PLEG불량/lease실패/scheduler CrashLoop/housekeeping지연)이 사실 한 원인 | CPU 순간 정지(soft lockup) 하나가 여러 하위 기능을 동시에 멈추게 함 | kubelet housekeeping 지연 시각과 커널 soft lockup 시각이 정확히 일치 |
| Node AGE ≠ VM uptime | 서로 다른 시계(K8s 오브젝트 나이 vs 커널 부팅 이후 시간) | Node 오브젝트는 재부팅해도 etcd에 유지되지만 uptime은 커널 기준 리셋 |
| vmstat의 steal(st) | 호스트가 CPU를 안 줘서 못 쓴 시간 비율 | steal=0이면 최소한 그 순간은 호스트 탓이 아니라는 판단 근거가 됨 |

## 다른 노드 Pod로 가는 길: 가짜 게이트웨이와 표 두 개

### 한 줄 요약
다른 노드의 Pod로 보낼 때, 커널은 **표를 두 번 조회**(ARP 표 → FDB 표)해서 "어느 노드 IP로 보낼지"를 알아낸 뒤 그 노드로 포장해서 보낸다. 이 조회를 시작시키는 주소가 **가짜 게이트웨이**다.

### 택배로 비유하면

| 택배 | 실제 네트워크 |
|---|---|
| 받는 사람 | 목적지 Pod IP (예: `10.244.1.5`) |
| 상대 지점의 접수 창구 번호 | **가짜 게이트웨이** `10.244.1.0` |
| 창구 번호 → 창구 명찰 | **ARP 표**: IP → MAC |
| 창구 명찰 → 지점 실제 주소 | **FDB 표**: MAC → 노드 IP (예: `10.10.0.11`) |
| 박스에 담아 배송 | VXLAN 포장 후 UDP 8472로 전송 |

### 가짜 게이트웨이가 뭔가
`10.244.1.0/24 via 10.244.1.0 dev flannel.1 onlink`에서 `via` 뒤의 `10.244.1.0`을 말한다.

- **진짜 라우터가 아니다.** 패킷을 대신 전달해 주는 장비가 없다.
- 하는 일은 하나: ARP 표와 FDB 표를 따라가서 **상대 노드 IP를 알아내게 하는 중간 주소**.
- 이 주소는 **상대 노드의 `flannel.1` 인터페이스 주소**일 가능성이 높다. 그래서 ARP 표에 "이 주소 = 상대 flannel.1의 MAC"이 미리 들어 있다.
  - 일반 지식이며 일지에서 직접 확인한 건 아님.
  - 확인하려면 워커에서 `ip -d addr show flannel.1`로 `10.244.x.0` 주소가 있는지 본다.

**왜 이렇게 만들었나?**
VXLAN은 이더넷 프레임을 포장하는 방식이라 목적지 MAC이 필요하다. Pod IP(`10.244.1.5`)로 MAC을 찾게 하면 flanneld가 Pod마다 표를 만들어야 하는데, Pod는 계속 죽고 생긴다. **노드마다 고정된 주소 하나**를 거치게 하면 표는 노드당 한 줄이면 된다.

### 4단계 과정

Pod IP `10.244.1.5`, 상대 노드 IP `10.10.0.11`은 설명용 가정이다. 실제 값은 일지에 없음.

| 단계 | 보는 곳 | 알아내는 것 | 확인 명령 |
|---|---|---|---|
| 1 | 라우팅 표 | "`10.244.1.x`는 `10.244.1.0`을 거쳐 flannel.1로 보내라" | `ip route` |
| 2 | **ARP 표** | `10.244.1.0`의 MAC은 `aa:bb:..` | `ip neigh show dev flannel.1` |
| 3 | **FDB 표** | MAC `aa:bb:..`은 노드 IP `10.10.0.11` 뒤에 있음 | `bridge fdb show dev flannel.1` |
| 4 | (포장) | `10.10.0.11`로 UDP 8472 전송 | - |

```
Pod IP(10.244.1.5)
  → ① 라우팅 표:  가짜 게이트웨이 10.244.1.0
  → ② ARP 표:     MAC aa:bb:..
  → ③ FDB 표:     노드 IP 10.10.0.11
  → ④ 포장해서 UDP 8472로 전송
```

### 헷갈리기 쉬운 점: ARP는 안 하는데 왜 ARP 표가 나오나?

| | 하는가 | 설명 |
|---|---|---|
| ARP **요청/응답** ("이 IP의 MAC이 뭐냐"고 네트워크에 묻는 동작) | 안 함 | flanneld가 표를 **미리 채워 둠** |
| ARP **표** 조회 (`ip neigh`) | 함 | 커널이 패킷을 보낼 때 이 표를 읽음 |

표는 읽지만, 표를 채우려고 네트워크에 묻지는 않는다.

### 8일차에서 이게 쓰인 곳
3단계 FDB 표(`bridge fdb`)에서 `dst`가 `172.17.x`(NAT망)로 나왔다. 의도한 건 `10.10.x`(Internal망)였다. 여기서 Flannel이 NAT망을 타고 있다는 걸 발견했다. (decisions/0003)

| 5 | (7일차) join에서 토큰과 CA 해시는 각각 누가 누구를 확인하나? | 토큰: 마스터가 워커를 확인. CA 해시: 워커가 마스터를 확인 | ⭕ (11/9에 이어 2회 연속) |
