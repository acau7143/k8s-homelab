## 한 줄 요약

**Docker는 컨테이너를 만들고 실행하는 도구이고, Kubernetes는 그 컨테이너들을 여러 서버에서 관리하는 시스템이다. 둘은 경쟁 관계가 아니라 역할이 다르다. 이 클러스터는 Docker 없이 containerd만 쓴다.**

비유: Docker = 주방장 한 명(요리 하나를 만든다), Kubernetes = 식당 체인 본사(여러 매장의 주방을 배치하고 관리한다).

---

## 컨테이너란

프로세스를 **격리해서 실행**하는 방식. 안에서는 자기만의 컴퓨터처럼 보이지만, 실제로는 호스트 리눅스 커널을 같이 쓴다.

- 컨테이너 = **namespace**(무엇이 보이는가를 격리) + **cgroup**(얼마나 쓸 수 있는가를 제한). 🔬 Day 4 복습에서 정리.
- 리눅스 namespace(커널 격리 기능)와 쿠버네티스 Namespace(오브젝트 분류)는 **이름만 같은 별개 개념**. 🔬 Day 8 Q&A. 차이는 아래 "namespace 두 가지" 참고.

### VM과의 차이

| | VM | 컨테이너 |
|---|---|---|
| 격리 방식 | 가상 하드웨어 위에 게스트 OS를 통째로 올림 | 호스트 커널을 공유하고 namespace/cgroup으로 격리 |
| 커널 | VM마다 따로 | 호스트와 공유 |
| 크기, 시작 속도 | 크고 느림 | 작고 빠름 |

- 🔬 이 프로젝트는 **VM 안에서 컨테이너를 돌린다**: VirtualBox VM 3대(Day 1~2)가 노드이고, 그 안에서 컨테이너가 실행됨.

## namespace 두 가지 (이름만 같은 별개 개념)

| | 리눅스 namespace | 쿠버네티스 Namespace |
|---|---|---|
| 정체 | **커널의 격리 기능** | 클러스터 안의 오브젝트를 나누는 **논리적 구획** |
| 무엇을 나누나 | 프로세스가 **볼 수 있는 것** (프로세스 목록, 네트워크, 파일시스템, 호스트명 등) | Pod, Service, Deployment 같은 **오브젝트의 이름과 범위** |
| 누가 만드나 | 컨테이너 런타임이 컨테이너마다 자동으로 | 사람이 `kubectl`로 만들고 오브젝트를 넣음 |
| 목적 | 컨테이너끼리 **격리** | 용도별로 **구분**, 이름 충돌 방지 |
| 예 | 한 Pod 안의 컨테이너들이 **네트워크 namespace 하나를 공유**해서 IP도 하나 (🔬 Day 8 Q&A) | `kube-system`, `kube-flannel` (🔬 Day 7, 9에서 `-n`으로 사용), `default` |

비유:
- 리눅스 namespace = **방의 벽**. 옆방이 안 보이게 막는다. (Day 4의 아파트 비유: 벽)
- 쿠버네티스 Namespace = **폴더**. 폴더가 다르면 같은 이름의 파일이 공존할 수 있다.

알아둘 점 (📖 일반 지식, 이 프로젝트에서 확인하지 않음):
- 리눅스 namespace에는 pid, net, mnt, uts, ipc, user 같은 종류가 있고, 컨테이너 하나가 이것들을 조합해서 자기만의 환경을 가진다.
- 쿠버네티스 Namespace는 **네트워크를 기본으로 막지 않는다.** 다른 Namespace의 Pod와도 통신이 된다. 막으려면 NetworkPolicy가 필요하다. 즉 "격리"가 아니라 "구분"이 기본 목적.
- 서로 다른 Namespace에는 같은 이름의 오브젝트를 만들 수 있다.

## 이미지, 컨테이너, 레지스트리

| 개념 | 뜻 | 비유 |
|---|---|---|
| **이미지** | 프로그램, 라이브러리, 설정을 묶은 **읽기 전용 설계도** | 요리 레시피 + 재료 키트 |
| **컨테이너** | 이미지를 **실행한 것** (같은 이미지로 여러 개 가능) | 키트로 만든 요리 |
| **레지스트리** | 이미지를 저장해 두고 내려받는 서버 (Docker Hub 등) | 키트 보관 창고 |
| **Dockerfile** | 이미지를 만드는 순서를 적은 파일 | 키트를 만드는 조리법 |

- 컨테이너는 일회용이라 컨테이너 안에 쓴 데이터는 컨테이너가 사라지면 같이 사라진다. 📖
- 🔬 Day 7: Flannel 설치 때 GitHub에서 받은 건 **YAML 설계도**뿐이고, 실제 프로그램(flanneld)은 **이미지 레지스트리에서 pull**됨. 이미지를 받아 띄우는 건 containerd.
- 🔬 `phase3-network/nginx-clusterip.yaml`: 이미지 `nginx:latest`로 Pod 2개. (`latest`는 버전이 고정되지 않음)

## Docker의 구성

Docker는 하나의 프로그램이 아니라 **여러 조각이 이어진 것**. 📖

```
docker CLI → dockerd(Docker 엔진) → containerd → runc → 컨테이너
 (사람이 치는 명령)   (이미지 빌드, 네트워크 등 편의 기능)   (이미지 관리,   (실제로 컨테이너
                                                       컨테이너 실행 관리)  프로세스를 만듦)
```

- **containerd**: 컨테이너 실행과 이미지 관리를 맡는 런타임. Docker의 한 부품이기도 하고, 단독으로도 쓸 수 있음.
- **runc**: 실제로 컨테이너 프로세스를 만드는 저수준 도구.
- Docker는 containerd 위에 이미지 빌드, CLI, 네트워크 같은 **사용자 편의 기능**을 얹은 것.

## Docker와 Kubernetes의 관계

| | Docker | Kubernetes |
|---|---|---|
| 하는 일 | 서버 **한 대**에서 컨테이너를 만들고 실행 | 컨테이너(Pod) 여러 개를 **여러 서버**에서 배치, 복구, 연결 |
| 다루는 단위 | 컨테이너 | Pod |
| 해결하는 문제 | "내 프로그램을 어디서나 똑같이 실행" | "컨테이너가 수십, 수백 개일 때 누가 어디서 돌지, 죽으면 어떻게 할지" |

- 쿠버네티스는 컨테이너를 **직접 실행하지 않는다.** 각 노드의 kubelet이 **CRI**(컨테이너 런타임과 대화하는 표준 규격)로 런타임에게 "이 컨테이너를 띄워라"라고 시킴. 🔬 Day 5 kubelet 정리 ("API 서버에서 맡을 Pod를 받아 containerd로 띄운다").
- 쿠버네티스 1.24에서 Docker Engine 직접 지원(dockershim)이 제거되어, 지금은 **containerd나 CRI-O** 같은 런타임을 쓰는 게 표준. 📖

### 이 클러스터는?

- 🔬 **Docker Engine 없이 containerd만** 사용. Day 4 일지에 `containerd.io-1.7.29` 설치만 있고 `docker-ce` 설치 기록은 없음.
- 🔬 `containerd.io` 패키지를 **Docker 공식 저장소**(`download.docker.com`)에서 받았지만, 받은 건 Docker Engine이 아니라 containerd 패키지.
- 🔬 그래서 컨테이너 런타임 상태는 `docker ps`가 아니라 `systemctl status containerd`, `journalctl -u containerd`로 확인 (Day 6).
- 🔬 `SystemdCgroup = true`: containerd가 cgroup 설정을 systemd에게 맡기도록 맞춰 둠 (Day 4).
- 📖 노드에서 컨테이너 목록을 직접 보려면 `crictl ps` 같은 CRI 도구를 쓰는데, 이 프로젝트에서 사용해 본 적은 없음.

## 이 프로젝트에서 컨테이너가 쓰이는 곳 (🔬)

| 컨테이너로 돌아가는 것 | 일차 |
|---|---|
| 마스터의 apiserver, etcd, scheduler, controller-manager (static pod) | Day 6 |
| Flannel (DaemonSet, 노드마다 1개) | Day 7 |
| kube-proxy, CoreDNS | Day 9 |
| nginx-test | Day 10 |

즉 쿠버네티스 자신의 핵심 부품도 전부 컨테이너로 돌아간다. 이 컨테이너들을 실제로 띄우고 감시하는 게 kubelet과 containerd.

## 자주 헷갈리는 것

| 질문 | 답 |
|---|---|
| 쿠버네티스는 Docker를 쓰나? | 이 클러스터는 안 쓴다. containerd가 컨테이너를 실행한다 (🔬) |
| 그럼 Docker는 이제 필요 없나? | 노드에서 컨테이너를 **실행**하는 용도로는 필요 없다. 이미지를 **빌드**하는 데는 여전히 많이 쓴다 (📖) |
| 컨테이너는 가벼운 VM인가? | 아니다. 커널을 공유하는 격리된 프로세스다 |
| 이미지와 컨테이너의 차이는? | 이미지는 설계도(읽기 전용), 컨테이너는 그걸 실행한 것 |
| Pod와 컨테이너의 차이는? | Pod는 컨테이너를 1개 이상 묶은 쿠버네티스의 배포 단위 |
